## Behavior and design deviations

- **FTS5 runtime-table exception:** Only the three persistent tables are declared in Drizzle and generated by drizzle-kit. retrieval_fts is an external-content FTS5 virtual table created at startup with unicode61/remove_diacritics=2. Code maintains INSERT/DELETE records; there are no triggers. Searches join live retrieval_chunks rows, so cascade-deleted orphans cannot be returned. Startup compares actual indexed document counts using a temporary fts5vocab view (external-content COUNT(*) would incorrectly count source rows), rebuilding on mismatch. Full rebuild also rebuilds FTS. Creation failure emits one warning per DB instance and uses normalized word-overlap scoring instead. Both FTS tables are derived caches, not hand-written migrations.
- retrieval_index uses the existing jobs queue, with the typed source/profile/all payload encoded after a retrieval_index: scope prefix and a RESEARCH storage stage. JobWorker dispatches it independently of the pipeline state machine and does not await embedding work before starting stages. No new queue table or pipeline stage was introduced. Pending jobs coalesce; another write within 30 seconds after a running/completed job schedules a delayed refresh instead of losing the edit.
- To preserve TASK-052 read-after-write behavior and keep its registry tests unchanged, memory edits refresh their text chunks immediately as well as enqueueing background embedding. The legacy search wrapper refreshes pending source text and retains overlap ordering over index results; pipeline and UI search use the specified RRF ranking. It no longer scans the 40 most recent projects on every query.
- Shared guideline packs are deduplicated within a profile and have no project id. Project-only rules remain attached to the project. This prevents generic shared rules from consuming the per-project diversity allowance intended for previous videos.
- Embedding models use an input with a datalist, permitting arbitrary custom/gateway model names as well as suggested choices. Custom endpoints require the explicit Hỗ trợ embedding toggle. Missing/failed/quota-limited embedding uses text retrieval; failed vectors remain null and are retried on subsequent applicable indexing/rebuild jobs.
- Previously covered topic candidates remain visible with đã làm plus an earlier project link, or đã xếp hàng for queued duplicates. They stay PENDING for review even when automatic approval is enabled. Duplicate entries within a single suggestion response are still counted/deduplicated.
- The context builder is called at the routed generation boundary with an explicit project and, for pipeline/review consumers, a query built from their existing brief/research/script/message. The block is appended before the existing prompt hash. No retrieval update marks a stage stale. A zero token budget leaves the prompt byte-identical.

| Provider | embed enabled | Documentation evidence |
|---|---|---|

| Gemini | Yes, delegated to its OpenAI-compatible endpoint | [Official OpenAI compatibility](https://ai.google.dev/gemini-api/docs/openai?linkId=13271420), indexed official page explicitly shows embeddings.create; [Google announcement](https://developers.googleblog.com/gemini-is-now-accessible-from-the-openai-library/) confirms the embeddings API. Direct fetching of the canonical docs returned an unsupported text/markdown error; official indexed content was available. |
| Ollama | Yes, OpenAI-compatible local endpoint | [Official source documentation](https://github.com/ollama/ollama/blob/main/docs/api/openai-compatibility.mdx), /v1/embeddings. |
| OmniRoute | Yes; user must select a routed embedding model | [Official API surface](https://omniroute.cheaperinference.com/api/), /v1/embeddings. Model support is checked by the normal embedding test; arbitrary chat models are not assumed to produce vectors. |
| Custom/custom-* | Explicit user opt-in | An arbitrary user's endpoint cannot be documentation-verified in advance; disabled until the user declares embedding support. |
| Mock | Yes | Deterministic normalized-word hashing into 64 dimensions, L2-normalized; fixture only. |
| CLI providers | No | Never embed. |
| Anthropic, native remote-ollama, OpenRouter, DeepSeek, Groq, OpenCode | No | Embedding endpoint support was not verified for these adapters; no capability was enabled. |

Batches are at most 32. Float32 blobs carry provider:model identity; vectors from another model are ignored. Calls respect quota/cool-down and write retrievalEmbed usage to the same job ledger consumed by UsageService, with the existing price estimator. Project ECO/CUSTOM embedding switches are respected for indexed project content.

## Retrieval fixture

Three independent query fixtures each contain a relevant explanation and six keyword-heavy distractor titles with unrelated bodies. Embeddings are produced by the deterministic mock word hasher, not a real semantic API. Query pairs: orbit stars, ocean coral, coffee beans. The fixture asserts both exact recall and the relevant explanation ranking first in hybrid mode.

| Metric | Text only | Hybrid |
|---|---:|---:|
| recall@5 | 0/3 = 0% | 3/3 = 100% |

This measures resilience to lexical/title noise on this small fixture, not general semantic quality or Vietnamese synonym recall with a production embedding model.
